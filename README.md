# arxiv-search

[![tests](https://github.com/Yasminenaser1/arxiv-search/actions/workflows/tests.yml/badge.svg)](https://github.com/Yasminenaser1/arxiv-search/actions/workflows/tests.yml)

[![tests](https://github.com/Yasminenaser1/arxiv-search/actions/workflows/tests.yml/badge.svg)](https://github.com/Yasminenaser1/arxiv-search/actions/workflows/tests.yml)

Semantic search over 50,000 ML paper abstracts — built to measure retrieval
quality and serving cost, not just to work.

**Live demo:** https://arxiv-search-mbrb.onrender.com
(free tier — first request may take ~50s while the instance wakes)

The interesting part of this project isn't the search. It's the four
measurements below, each of which changed a design decision.

---

## Results

50,000 abstracts, 50 LLM-generated queries with one known-relevant document
each. Latency measured locally (M-series Mac, CPU-only).

| Config | recall@1 | recall@5 | recall@10 | MRR@10 | p50 |
|---|---|---|---|---|---|
| Dense (all-MiniLM-L6-v2) | 0.440 | 0.640 | 0.700 | 0.528 | 3.2ms |
| BM25 | 0.560 | 0.760 | 0.800 | 0.643 | 49ms |
| Hybrid (RRF) | 0.580 | 0.760 | 0.880 | 0.670 | 54ms |
| Hybrid + rerank top-20 | 0.700 | 0.880 | 0.920 | 0.776 | 106ms |
| **Hybrid + rerank top-50** | 0.700 | 0.880 | **0.940** | **0.780** | 177ms |
| Hybrid + rerank top-100 | 0.700 | 0.880 | 0.920 | 0.777 | 291ms |

An earlier run on 10,000 documents hit recall@10 = 1.000 and could no longer
measure improvement. Scaling 5× restored headroom — every number above is
lower, which is what makes them useful.

## Five findings

**1. BM25 beat the neural model — but only because of how the queries were
written.** A 2009 keyword-matching algorithm outscored sentence-transformers
on every quality metric (MRR 0.643 vs 0.528), and the gap widened at 5× scale
(0.067 → 0.115). That looked like a finding about retrieval. It wasn't. The
eval queries were generated by an LLM reading each abstract, so they inherit
the paper's vocabulary, and exact term overlap is a powerful signal when the
query reuses the document's words. I tested this by rewriting 20 queries to
describe each paper without its technical terms — see "Vocabulary dependence"
below. BM25's MRR fell to 0.025.

**2. Reranking depth has a knee, and past it you pay for nothing.**
Top-50 and top-100 are identical on every metric. The extra 50 candidates
cost 126ms and changed no rankings.

**3. Reranking costs 40× throughput.** Under load: 1.8 req/s with the
cross-encoder, 71 req/s without, for an 11% MRR gain. p50 climbs from
517ms to 1435ms as concurrency goes 1→8 while throughput stays flat —
requests queue rather than parallelize, because the model is CPU-bound and
serialized. This is why the deployed version has reranking disabled.

**4. Offline benchmarks don't transfer to production.** Retrieval measured
0.5ms offline and 41ms in the API — the eval batch-encoded all queries at
once, while the server encodes one per request. On Render's free CPU the
same code takes 727ms cold p50 — measured from the deployed dashboard, not
estimated. Same implementation, three very different
numbers depending on how it's called and where it runs.

---

**5. The system had no concept of "no results."** Searching for something
entirely outside the corpus — "how to make sourdough bread" — returned ten
confidently-ranked papers. Cosine similarity always has a nearest neighbour and
RRF always produces a ranking, so nothing in the pipeline could say "nothing
here." The cross-encoder scores turned out to separate: relevant queries score
roughly +2 to +4, clearly irrelevant ones cluster near -11. Thresholding at -5
gives an honest empty state, and the signal was already being computed on every
reranked query — nothing was reading it.

Partial relevance has no clean cutoff: a speech-recognition query against this
ML corpus scored -6.4, neither a match nor nonsense. The floor catches obvious
cases only. These are also unbounded logits rather than probabilities, so they
can't be shown to users as confidence without calibration.

## Vocabulary dependence — the biggest caveat

Every number in the results table assumes the query is phrased in the paper's
own technical vocabulary. When it isn't, the whole system fails.

I built a second 20-query eval where each query describes the paper in plain
language, avoiding its distinctive terms — "spotting short events in brain
recordings taken while someone sleeps" instead of "detecting sleep
micro-events in EEG signals."

| Eval set | Dense MRR@10 | BM25 MRR@10 |
|---|---|---|
| Original (LLM-generated from abstracts) | 0.528 | 0.643 |
| Paraphrased (technical terms removed) | 0.061 | 0.025 |

Both methods collapse. Dense holds up ~2.4× better than BM25 and finds papers
BM25 misses entirely, which is the expected direction — but 0.061 is still a
system failing 94% of the time, not a win.

So the reported metrics describe a narrow and favorable case: users who
already know the field's terminology. A newcomer describing what they want in
plain language would get almost nothing back. Fixing that needs a better
embedding model or query expansion, neither of which is in scope here.

Two caveats on this experiment: the paraphrased queries were drafted with LLM
assistance rather than written cold by a domain expert, so they're a weaker
probe than true human queries; and 20 queries is a small sample.

## Honest limitations

- **Single-gold labeling understates quality.** Each query has exactly one
  document marked relevant, but the corpus contains many papers on the same
  topic. Spot-checking 6 queries by hand, roughly 13 of 15 top-3 results
  were genuinely relevant despite counting as misses. Metrics here are valid
  for *comparison*, not as absolute quality.
- **50 queries is a small sample.** One query moving is worth ~0.02 MRR.
  Differences of that size are suggestive, not conclusive.
- **An easy eval tier was discarded.** Title-derived queries scored 0.966
  MRR because the query text appears inside the indexed document — a
  leakage bug, not a good score.
- **Chunking was considered and skipped.** Abstracts are ~200 words, well
  under the model's context limit, so there was nothing meaningful to chunk.

## Production differs from the best config

The deployed service runs **hybrid retrieval with reranking disabled, over
3,000 documents** — while all measurements above were taken locally on 50,000
documents with reranking available. The live demo is therefore a deliberately
weaker configuration than the one benchmarked. Render's free tier
gives 512MB RAM and one weak CPU, and the reranked path would push a single
user past a second per query. Measuring the best config and then shipping a
cheaper one is the actual tradeoff, so it's documented rather than hidden.

## Architecture

- **Dense:** `all-MiniLM-L6-v2`, 384-dim, normalized (cosine = dot product)
- **Sparse:** BM25Okapi over title + abstract
- **Fusion:** RRF — combines *ranks*, not scores, so the two scales never
  need normalizing. A k-sweep from 10 to 100 moved MRR by 0.004, so the
  parameter doesn't matter here.
- **Rerank:** `ms-marco-MiniLM-L-6-v2` cross-encoder
- **Cache:** LRU over the full result, 512 entries — 0.8ms warm vs 517ms cold

## Running it

```bash
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

python fetch.py        # 50k abstracts from HF (CShorten/ML-ArXiv-Papers)
python embed.py        # → data/embeddings.npy
python bm25_index.py   # → data/bm25.pkl

python -m uvicorn api:app --port 8000
```

Then http://127.0.0.1:8000 for search, `/dashboard.html` for live metrics.

**Reproduce the measurements:**

```bash
python run_evals_compare.py evals/hard.json   # dense vs BM25
python hybrid.py evals/hard.json              # + RRF, k sweep
python rerank.py evals/hard.json              # + reranker depth sweep
python loadtest.py                            # concurrency, p50/p95
```

## Notes

- Fully local, no API keys, no paid services.
- `deploy_data/` (3k docs) is committed so deploys are reproducible;
  the 50k local corpus is regenerated by `fetch.py`.
- Model calls are serialized behind a lock — PyTorch's MPS backend isn't
  thread-safe under a concurrent server, so the models run CPU-only.
